# ds-poc

POC comparing two ways of implementing the **same** design system in Vue:

- **`apps/ds-reka`** — components written directly on top of [`reka-ui`](https://reka-ui.com) primitives, styled with [`class-variance-authority`](https://cva.style) and Tailwind v4.
- **`apps/ds-shadcn`** — components generated by the real [`shadcn-vue`](https://shadcn-vue.com) CLI (`init` + `add`), then edited to consume the same design system tokens.

Both apps consume the **same tokens package** (`packages/tokens`, Style Dictionary v4, DTCG `$value`/`$type` format), which generates CSS with a `--ds-*` prefix. No color/spacing/radius/typography value is duplicated or diverges between the stacks — the only variable is where the component code comes from.

## Structure

```
ds-poc/
├── packages/tokens/   # Style Dictionary — single source of truth for the tokens
└── apps/
    ├── ds-reka/       # Stack A: reka-ui directly
    └── ds-shadcn/     # Stack B: shadcn-vue (real CLI) + re-tokenizing
```

## Technical decision: Tailwind v4 and the tokens

Tailwind v4 is CSS-first (no `tailwind.config.js`/`theme.extend`). In both apps, `src/style.css` imports `@ds-poc/tokens/css` (the `--ds-*` variables) and remaps them into Tailwind's theme namespace inside an `@theme` block:

```css
@import "tailwindcss";
@import "@ds-poc/tokens/css";

@theme {
  --color-brand-600: var(--ds-color-brand-600);
  --radius-md: var(--ds-radius-md);
  /* ... */
}
```

This is the v4-native equivalent of Tailwind v3's `theme.extend`, and it's **identical** in both apps.

## About running the shadcn-vue CLI "for real"

The CLI was actually executed (`npx shadcn-vue ... init` and `add`), not simulated. During the run, the `@latest` version (2.8.2) showed a real, reproducible network bug: the concurrent requests that `init` makes against `shadcn-vue.com/r/*` consistently fail *inside* the CLI process (`Failed to fetch from registry: .../r/styles/index.json`), even though the exact same call, in isolation, works fine (verified via `curl`, via `node -e "fetch(...)"`, and via an `ofetch` call identical to the one used internally by the CLI). This isn't a network issue in the environment — it's a regression specific to the `init` flow of the latest version.

Given that, `init`/`add` were run with `shadcn-vue@2.6.2` (the last stable version before this issue, same reka-ui + CVA + `--base reka` architecture). Commands used, inside `apps/ds-shadcn`:

```
npx shadcn-vue@2.6.2 init -y --base reka --style vega --icon-library lucide --font inter -b neutral --template vite --no-rtl
npx shadcn-vue@2.6.2 add button switch dialog -y
```

The raw output of that command was committed on its own (commit `c4a2325`, "raw CLI output") before any manual edits, so the real editing effort could be measured via `git diff --stat` against the final commit (`8671713`).

Additional leftovers, at the project level (not per component): the Inter font import via Google Fonts and the entire `oklch` theme (background/foreground/card/popover/muted/accent/destructive/ring/input/border + `.dark` dark mode + `sidebar`/`chart-1..5` tokens) generated by `init` in `src/style.css` — none of it has an equivalent in the DS tokens, so the whole file was replaced with the same `@theme` block used in ds-reka.

The `cn()` helper (`clsx` + `tailwind-merge`) was **kept** as the CLI generated it — the `ui/*` components keep using `cn()` to merge variant classes (CVA) with overrides via the `class` prop; that decision is documented in a comment at the top of `src/lib/utils.ts`.

## Effort: Button vs. Switch/Dialog

- **Button** (a "dumb" component, no behavior): comparable effort in both stacks. In ds-reka, it's plain CVA from scratch. In ds-shadcn, the CLI already delivers a correct CVA base — but the generated `Button.vue` needed zero edits, and the real work was trimming variants/sizes that don't exist in the DS and re-tokenizing `index.ts`. In the end, ds-shadcn ended up with **more lines** (62 vs. 45) because the generated structure splits `Button.vue`/`index.ts` and keeps more metadata (`data-slot`, `data-variant`, types via `PrimitiveProps`) than the hand-written minimal version.
- **Switch and Dialog** (with behavior — focus trap, Escape, `v-model`, portal/overlay): here ds-shadcn's initial speed advantage is real — `SwitchRoot`/`SwitchThumb` and the whole `Dialog*` set (including accessibility, `DialogTitle`/`DialogDescription` via `aria-labelledby`/`aria-describedby`, close-on-Escape, focus trap) come out of `add` ready to go, with none of it needing to be hand-written. The cost shows up later: shadcn-vue's Dialog is *modular* (11 files/280 lines in the `ui/dialog` folder, of which only 8/176 are used in this DS's stories) versus 1 file/59 lines in ds-reka — more composition power (Header/Footer/ScrollContent ready for other cases), but also more files to review, re-tokenize, and maintain. For this minimal DS (3 components, 5 colors, 3 radii), ds-reka ends up leaner; for a larger DS with many Dialog variations, shadcn-vue's modularity tends to pay off faster.

In short: shadcn-vue's speed gain is proportional to how behaviorally complex the component is, but it comes bundled with a footprint of files and conventions (oklch tokens, `data-slot`, `cn()`, extra variants) that needs to be trimmed/re-tokenized — work the Button doesn't require, but that shows up in full on the Dialog.

## Running both Storybooks side by side

```bash
pnpm install
pnpm build:tokens   # generates packages/tokens/dist/css/variables.css

pnpm --filter ds-reka storybook    # http://localhost:6006
pnpm --filter ds-shadcn storybook  # http://localhost:6007
```

(Each app's `predev`/`prebuild`/`prestorybook` already runs the tokens build automatically before the respective command — the manual step above is just to make the generated CSS available on the first run.)

Each app also runs standalone with `pnpm --filter ds-reka dev` / `pnpm --filter ds-shadcn dev` (Vite dev server, default Vite ports).
